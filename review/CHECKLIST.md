# 审查核对表 · shardprng

> 本表只规定**交付格式与自检项**，不给出缺陷数量、位置或现象。
> 结论一律写进 `review/REVIEW.md`，本表**勿改**。

## 一、交付物

- 唯一交付物：`review/REVIEW.md`（本目录下）。
- 不改 `shardprng/`、`tests/`、`repro.py`、`scripts/`、`check/`、`README.md`、本文件。
- 不新增源码文件；临时验证脚本可以写，但**不要留在仓库里**（跑完删掉）。
- 提交前用 `git status --short` 自检：除 `review/REVIEW.md` 外不应有其它改动。

## 二、结论的写法

`review/REVIEW.md` 里用 `### 结论 1`、`### 结论 2` …… 这样的小节逐条写结论；
每个小节里用下面 4 个字段（**缺一样就不算一条结论**）：

| 字段 | 含义 | 要求 |
| --- | --- | --- |
| `保证编号` | 被违反的是 README「对外保证」里第几条 | 写 1~8 的整数 |
| `缺陷位置` | 出错的具体代码位置 | 写成 `文件:行号`，如 `shardprng/foo.py:12` |
| `复现命令` | 能稳定复现的最小命令 | **一行 bash 命令**，以 `python3` 起头，可直接照抄运行 |
| `实际输出` | 跑出来的具体现象 | 把命令的真实输出贴出来（期望什么 / 实际什么要能对上） |

`复现命令` 只允许用本仓库代码与 Python 标准库，不要引入第三方依赖，
也不要写管道、重定向之类的组合命令；**不许用系统 `random` 或 `time`**，
要复现就用固定输入（固定种子、固定键集），否则证据本身不可复现。

## 三、固定验收怎么判

`bash scripts/check.sh` 只校验下面这些**格式与可复现性**的事实，结论正确与否由人按 README 逐条复核：

- `REVIEW.md` 有「结论」章节，且已经填好（不是空模板）；
- 结论条数 ≥ 6；
- 每条结论的 4 个字段都非空，`缺陷位置` 写成 `文件:行号` 且文件真实存在、行号在文件范围内；
- 每条结论的 `复现命令` 都能在本仓库根目录下真实跑起来（以 `python3` 起头、退出码为 0 或 1）并产生输出；
- 全部结论合计至少引用 5 条**不同**的对外保证，且每条结论指向**不同**的缺陷位置；
- 不可改文件（`shardprng/`、`tests/`、`repro.py`、`scripts/`、`check/`、`README.md`、本文件）的
  SHA-256 与文件清单都没变。

> `integrity` 两项在 `REVIEW.md` 还是一张空模板时不会通过——先有交付物，才谈得上「没有靠改源码制造结论」。

## 四、自检项

- [ ] 每条结论都能对应到 README 里**某一编号**的对外保证。
- [ ] 每条结论都给出了**可照抄复现**的命令与**具体现象**（期望 vs 实际）。
- [ ] 没有「可能有风险」「建议关注」「看起来不太对」「或许」这类**无法核对**的话。
- [ ] 只写「违反了哪条保证」与证据，**不写修复建议**。
